# 《忘却前夜》编队分享码格式逆向记录

## 结论

编队分享码不是加密文本、Base64、压缩数据或服务器生成的随机 ID。它是一个确定性的、区分大小写的紧凑字典编码：

1. 每个唤醒体、命轮、密契和钥令都有一个专用的 `lineupToken`。
2. 空值使用保留 token `a`。
3. 游戏按固定的 17 个逻辑字段排列这些 token。
4. 将 token 直接连接，不插入分隔符。
5. 在首尾各加 `@@`。

完整的“调查行动——编队分享”文字只是本地化展示外壳。实际可导入内容只有：

```text
@@<payload>@@
```

单独把这一段放进剪贴板也可以导入。玩家名、UID 和队伍名不在 payload 中。

## 17 个字段的固定顺序

| 逻辑字段 | 数量 | 顺序                                    |
| -------- | ---: | --------------------------------------- |
| 唤醒体   |    4 | 1 号位至 4 号位                         |
| 命轮     |    8 | 1 号位命轮 1、命轮 2，然后 2、3、4 号位 |
| 密契     |    4 | 1 号位至 4 号位                         |
| 钥令     |    1 | 当前队伍钥令                            |

因此字段序列为：

```text
A1 A2 A3 A4
W1a W1b W2a W2b W3a W3b W4a W4b
C1 C2 C3 C4
P
```

这里的空格和换行仅用于说明，实际 payload 中没有分隔符。

## token 规则

- token 区分大小写；例如 `b` 与 `B` 是两个不同值。
- `a` 是通用空值，不对应正常实体。
- 当前数据中的正常 token 长度为 1 或 2 个 ASCII 字母/数字。
- 唤醒体的双字符 token 当前以 `x` 开头。
- 命轮的双字符 token 当前以 `x`、`y` 或 `z` 开头。
- 密契和钥令在当前数据中都是单字符 token。
- 同一 token 可以在不同类别中代表不同实体，所以必须按当前字段类别查询。
- 每个类别内的 token 集合是前缀无冲突的，可以使用该类别的 trie 或最长匹配来读取。不要把 payload 机械地逐字符拆分。

仓库中的显式映射位于：

- `data/records/awakeners/*.json`
- `data/records/wheels/*.json`
- `data/records/covenants/*.json`
- `data/records/posses/*.json`

对应 JSON 字段均为：

```json
{
  "lineupToken": "..."
}
```

`posses` 是项目数据模型中钥令所使用的记录类别。

仓库快照中有 59 个唤醒体、140 个命轮、21 个密契和 53 个钥令 token。逐类别检查的结果是：token 均区分大小写后唯一，且类别内没有前缀冲突。另有 8 个无 token 的历史钥令记录仅用于兼容旧存档，不可新选。

## 用户提供样本的完整拆解

原 payload：

```text
xjwOvyVxhvRxXro6vBnw2

|    3 | 泰旖丝 | `O`   |
|    4 | 宁菲亚 | `v`   |

```

### 密契

| 位置 | 实体        | token |
| ---: | ----------- | ----- |
|    1 | 无垢启示录  | `v`   |

|    3 | 生机榨取    | `n`   |
|    4 | 荒原狼      | `w`   |

```text
vBnw
```

### 钥令

| 实体     | token |
| -------- | ----- |
| 深宅往事 | `2`   |

连接四段：

```text
xjwOv + yVxhvRxXro6 + vBnw + 2
= xjwOvyVxhvRxXro6vBnw2
```

加上外层标记后即与原码逐字相同：

```text
@@xjwOvyVxhvRxXro6vBnw2@@
```

## 生成算法

第三方编队器不应从显示名、资源 ID 或配置 ID 推导 token，而应把 `lineupToken` 当成随游戏版本发布的数据。

```js
const EMPTY_TOKEN = "a";

function tokenOf(entity) {
  return entity?.lineupToken ?? EMPTY_TOKEN;
}

function encodeTeam(team) {
  const slots = team.slots; // exactly four slots

  const fields = [
    ...slots.map((slot) => slot.awakener),
    ...slots.flatMap((slot) => [slot.wheels[0], slot.wheels[1]]),
    ...slots.map((slot) => slot.covenant),
    team.posse, // keyflare
  ];

  return `@@${fields.map(tokenOf).join("")}@@`;
}
```

不存在额外校验和、签名、随机盐或 UID 字段。受控实验中，单独替换第一个唤醒体 token 后，游戏仍能解析并导入，进一步排除了全局校验和。

## 解析算法

1. 从剪贴板文字中提取 `@@([A-Za-z0-9]+)@@`。
2. 使用唤醒体 token trie 依次读取 4 个值。
3. 使用命轮 token trie 依次读取 8 个值。
4. 使用密契 token trie 依次读取 4 个值。
5. 使用钥令 token trie 读取 1 个值。
6. 确认 payload 已全部消耗，否则视为版本不匹配或无效码。
7. 每个类别的 trie 都应额外注册 `a -> null`。

不要使用一个全局 token 表，因为相同字符串在不同类别中可以有不同含义。

## 空位和未持有内容

空字段固定写成 `a`。实测空编队、仅保留钥令的 payload 为：

```text
aaaaaaaaaaaaaaaaG
```

即 16 个空字段加 1 个钥令 token。

另一个部分编队样本：

```text
@@xtWaaaaaaaaaaaaaac@@
```

可解析为前两个唤醒体 token `xt`、`W`，其余 14 个编队字段为空，最后钥令为 `c`。

导入时，游戏会先解析 token，再检查账号是否持有对应配置。未持有的部分会被清空；这不是分享码格式错误。第三方编队器最好在复制前提示玩家：导入结果受目标账号持有情况影响。

## 版本同步风险

`lineupToken` 是显式映射数据，不是可以安全地从 `AwakerConfig` ID、名称或列表下标重新计算的值。仓库记录能解释绝大多数样本，但它不是与当前安装客户端完全同步的快照。

已用当前客户端和真实分享码确认的差异包括：

| 实体      | 当前客户端/真实码 | 仓库记录   |
| --------- | ----------------- | ---------- |
| 徐        | `xj`              | `xk`       |
| 沙耶      | `xk`              | `xl`       |
| 莫丝      | `xm`              | `xo`       |
| 枉蹙眉    | `yV`              | `yX`       |
| 蚀灭·萝坦 | `xt`              | 无对应记录 |

此外，当前客户端拒绝把单字符 `0` 当作完整的第一个唤醒体 token，而仓库中的皮克曼记录仍写作 `0`。这也是不能盲信旧快照的直接证据。

仓库旧式展示数据与带 token 的 records 覆盖量也不一致：

| 类别   | 旧式展示数据 | 带 `lineupToken` 的 records |
| ------ | -----------: | --------------------------: |
| 唤醒体 |           59 |                          57 |
| 命轮   |          138 |                         134 |
| 密契   |           23 |                          21 |
| 钥令   |           51 |                          51 |

因此生产实现应：

- 为 token 字典记录游戏版本或数据版本。
- 每次新增角色、命轮、密契或钥令时同步官方/客户端配置中的显式 token。
- 用至少一个真实导出码做回归测试。
- 对未知 token 给出“数据版本过旧”，不要猜测映射。
- 暂时以本节的当前客户端实测值覆盖仓库中的已知过期值。

## 受控验证记录

所有会改变游戏编队的实验都只在用户授权的第 10 队进行；第 11 队未被改动。其他队伍只读取了现有分享内容。

已确认：

- 同一编队重复复制得到完全相同的 payload。
- 单独的 `@@...@@` 片段可导入，不需要分享文案。
- `a` 表示空值。
- `b` 可作为第一个唤醒体 token 导入潘狄娅。
- `A` 可导入弥利亚姆。
- `X` 可导入塔薇。
- `9` 可导入克莱门汀。
- `x` 单独不是完整唤醒体 token；它是双字符 token 的前缀。
- 大小写和字符位置都会改变实体含义。
- 未持有实体会在确认导入后被游戏清空。

这些结果与仓库中 `lineupToken` 的数据结构、多个现有队伍的分享码以及用户提供样本的逐字段重建相互吻合。
